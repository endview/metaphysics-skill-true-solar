# 玄学 Skill 可靠执行与跨环境稳定性优化方案

> **文档版本：**1.0  
> **文档性质：**设计与实施方案，不代表相关改造已经完成。  
> **适用项目：**`endview/metaphysics-skill-true-solar`  
> **审查基线：**`456100131d7f0492df9ac1d515d614d37515f9da`  
> **核心顺序：**执行证据 → 个案与时间管理 → 回归测试 → 解释约束 → 工具扩展。

## 1. 方案摘要

本次改造保留现有四个 Skill，不推翻主路由与独立子方法的结构，也不以增加术数种类为目标。

优化的中心是：

**让“已执行、可复用、可比较、可交付”成为有证据和检查条件的状态，而不是模型在回答中自行宣布的状态。**

最终形成一条可检查的执行链：

```text
识别任务与能力
    ↓
绑定对象、事件、命题与时间范围
    ↓
确认必要输入并冻结个案
    ↓
实际调用子方法计算器
    ↓
保存执行记录并校验原生结果
    ↓
生成有依据、有限度的解释
    ↓
校验标准子结果及自然语言事实块
    ↓
满足条件时组合，否则交付单项结果或明确缺口
```

产品形态保持为：

| Skill | 职责 |
|---|---|
| `$metaphysics` | 选择能力、拆分任务、分派、适配与综合 |
| `$analyze-bazi` | 八字结构检查及其声明支持的解释层 |
| `$analyze-ziwei` | 真太阳时来源确认后的紫微事实盘与领域解释 |
| `$cast-meihua` | 固定协议下的起卦与有界问题的象征性解释 |

新增的是轻量执行支撑、校验器、个案记录、知识卡和测试资产，不是新的包办型 Agent 平台。

## 2. 现状、证据与问题边界

### 2.1 已确认的基线

本次读取的 `main` 仍指向上述基线提交。README 声明四个 Skill 自包含、主路由不执行子方法算法、正式包不保存用户资料；此前讨论过的优化不能因此视为已实现。 

| 检查项 | 当前状态 | 本次处理 |
|---|---|---|
| 主路由与三个子 Skill | 已存在 | 保留职责边界 |
| 梅花确定性计算器 | 已存在 | 不改变既有取数算法 |
| 紫微内置引擎及完整性校验 | 已存在 | 保留，优化加载与执行包装 |
| 八字结构检查器 | 已存在 | 不冒充历法排盘引擎 |
| 执行、个案、解释之间的强绑定 | 主要依靠模型遵守契约 | 增加程序检查 |
| 仓库级测试和发布门禁 | 基线树中未见完整体系 | 本次建设 |
| 通用时间工具、独立知识 provider | 保留但未启用 | 不因本方案直接激活 |

### 2.2 已有审计产物的使用方式

提供的 `meihua-audit-results.json` 记录了 **468 项检查全部通过**，包括384组卦形与动爻组合、48项小时边界检查和36项其他检查。记录环境为 Node.js `v22.16.0`、ICU `77.1`。

本轮核读确认测试条目数与汇总数字一致，但**没有重新执行其全部测试**。该产物也不包含完整的语言模型端到端验证、紫微全链验证或现实预测效度证明。

实施时必须补齐测试源码、合成夹具、运行命令和复现环境。只有报告、没有可复现测试工程，不能充当新版本发布门禁。

### 2.3 需要修复的主要失效模式

| 编号 | 失效模式 | 根因 | 修复方向 |
|---|---|---|---|
| F01 | 读取源码后声称已经运行 | 加载与执行未分离 | 执行记录与工具来源绑定 |
| F02 | 正确结果被转述为错误卦名或时辰 | 自由文本重新计算 | 确定性事实块与输出检查 |
| F03 | 感情个案被用于求职 | 只记数字或卦名 | 对象、事件、命题联合绑定 |
| F04 | 改期限或换算法就重新起卦 | 个案生命周期不明确 | 冻结、修订、复用和重起分别处理 |
| F05 | 相对阶段被写成具体日期 | 输出精度没有上限 | 时间精度契约 |
| F06 | 缺少紫微输入仍补造宫位 | 为满足组合数量模拟结果 | 分支就绪检查和部分交付 |
| F07 | 象征解释变成读心或定位 | 免责声明不能限制正文推断 | 分层主张、知识卡、行为测试 |
| F08 | 单上下文被称为独立多方法核验 | 加载能力与隔离能力混淆 | 宿主能力声明 |
| F09 | 新现实信息被说成旧卦早已预测 | 事实来源与解释版本混合 | 现实证据单独更新，禁止回写 |

这些失效并不都意味着原生计算器存在缺陷。改造重点是计算器之外的输入、调用、复用、解释和交付链路。

## 3. 目标与非目标

### 3.1 必须达到的目标

**执行可查。** 每次正式计算能关联到冻结输入、实际调用、原生结果和校验记录。

**个案不串。** 相同数字、卦象、姓名标签或话题词不能成为跨任务复用依据。

**时间一致。** 日期、时区、精度、口径和期限来源明确；解释不得比依据更精细。

**边界明确。** 缺失能力、缺失输入、运行失败、结果不兼容分别处理，不通过模型自由发挥补齐。

**输出不过度推断。** 计算事实、传统解释、现实资料、行动建议可以区分；符号不作为隐藏事实的证据。

**跨环境诚实。** 能加载、能执行、能隔离、能持久化分别声明，不用一个“支持 Skill”概括全部能力。

**运行不过重。** 没参与当前任务的子方法、引擎和知识卡不进入默认上下文。

### 3.2 本次不做

不增加六爻、奇门等方法；不建设古籍全文检索平台；不做自动校时、人生事件反选命盘、多方法投票或预测准确率。

不开发数据库、消息队列、分布式调度平台；不默认激活 `knowledge`、`utility`、`workflow` provider。

不把可靠执行等同于现实预测有效。工程验收只评价协议、计算、来源、隔离和表达是否符合要求。

## 4. 总体架构与职责

### 4.1 三个层面

| 层面 | 主要职责 | 不承担的职责 |
|---|---|---|
| Skill 语义层 | 理解问题、收集必要输入、按知识卡解释 | 伪造工具执行、自行提升证据等级 |
| 轻量执行层 | 个案冻结、调用、结构校验、引用检查、打包 | 代替模型理解所有自然语言、执行术数解释 |
| 宿主环境层 | 工具调用记录、进程、上下文隔离、授权存储 | 由 Skill 文本自动创建宿主原本没有的能力 |

主路由只处理编排，不复制子方法取数表、排盘算法或原生载荷。三个子 Skill 在单独安装时也经过相同的本地执行与校验路径。

### 4.2 硬约束与软检查分开

能够确定性检查的内容必须程序化：状态枚举、数字、日期、时区、引用、哈希、对象标识、版本、重复执行、卦形一致性。

自然语言推断的合法性不能仅靠正则表达式保证。采用：

**受约束解释结构＋风险规则＋对话回归＋抽样人工复核。**

不宣称自动检查器能够完全识别读心、事后拟合或误导性措辞。

## 5. 默认存在与按需加载

“安装到磁盘”不等于“常驻模型上下文”；“代码可调用”也不等于“每轮必须完整读取代码”。Agent Skills 规范支持元数据、主指令和资源分层加载。

| 内容 | 默认是否进入上下文 | 加载时机 |
|---|---|---|
| 四个 Skill 的名称与简短描述 | 由宿主提供时是 | 用于发现与触发 |
| 当前 Skill 的入口规则 | 否 | 激活对应 Skill 后 |
| 主路由能力清单 | 否 | 需要推荐或编排时 |
| 详细编排契约 | 否 | 实际分派、综合、复用或错误处理时 |
| 个案核心摘要 | 仅当前任务需要的部分 | 冻结、继续或复盘当前个案时 |
| 子方法算法脚本 | 不全文注入语言上下文 | 由执行器按固定入口调用 |
| 紫微 vendor 引擎 | 否 | 紫微预检通过并确需排盘时 |
| 知识卡 | 否 | 按本轮结构、领域和时间层选择 |
| 完整原生 JSON、调试日志 | 否 | 校验器消费；用户审计时按需展示 |
| 测试和开发文档 | 否 | 开发、审查、CI 使用，发布包排除 |

入口只保留触发条件、最短执行流程、必须遵守的边界及直接引用。

运行器复用同一请求中已经校验过的只读资源，资源内容或版本变化后失效缓存。不得把整个用户历史当作默认个案库加载。

## 6. 核心数据契约

新增契约集中解决跨层绑定，不在每个阶段复制完整结果。

| 对象 | 关键字段 | 用途 |
|---|---|---|
| `metaphysics.case.v1` | `case_id`、`revision`、`subject_ref`、`event_ref`、`proposition_id`、`question`、`window`、`criteria`、`method_inputs_ref` | 标识问题与冻结条件 |
| `metaphysics.time-context.v1` | `source_kind`、`raw_input`、`instant`、`timezone`、`input_precision`、`time_basis`、`resolution_status`、`source_ref` | 时间来源与精度 |
| `metaphysics.execution-record.v1` | `run_id`、`case_id`、`task_id`、`attempt`、`entrypoint`、`source_digest`、`input_digest`、`output_digest`、`exit_code`、`observation` | 实际执行事实 |
| `metaphysics.runtime-capabilities.v1` | 加载方式、进程能力、Chinese calendar、隔离方式、工具观察能力、存储范围及其来源 | 决定实际能执行什么 |
| `metaphysics.execution-bundle.v1` | `binding`、`execution_ref`、`validation`、`child_result` | 把执行证据和标准子结果绑定 |

### 6.1 唯一载荷原则

`child_result` 仍采用 `metaphysics.standard-child.v1`。完整原生内容只在其 `method_payload` 中保存一次。

执行记录只保存结果引用及摘要，不再嵌套一份完整 JSON。主路由适配后也只保存一份原生载荷。

既有计算器的原生格式与标准子结果本来就不同，不把这种分层误判为 bug。新增包装器负责检查和衔接，不把原生结果直接改名为标准子结果。

### 6.2 标识与语义分开

`case_id` 等标识由执行支撑层或宿主生成。对象标签可以是“本人”“朋友A”“商品A”，不得因标签相同就默认是同一现实对象。

可以使用规范化输入摘要辅助去重，但摘要只判断字节或结构一致性，不判断两个自然语言问题是否同义。语义有歧义时保留待确认状态。

### 6.3 引用规则

新结果的 `basis_refs` 采用约定的 JSON Pointer 路径，指向该分支 `method_payload`；路径格式写入对应验证 profile。

旧路径表达式只由已登记的兼容适配器解析。无法解析、指向别的分支、引用不存在字段的主张不进入综合。

**能解析路径，也不代表该字段确实支持整句主张。** 后者仍需解释层检查。

### 6.4 核心不变量

所有标识必须在对应作用域内唯一；分派中的对象和命题标识由子分支原样返回。

执行记录的输入摘要必须匹配当前冻结修订，结果摘要必须匹配实际保存的载荷。

`execution-bundle.v1` 只能包含一个 `child_result`，其方法、case和task绑定必须与执行入口一致。

验证报告必须引用同一载荷摘要；更换载荷后，旧验证报告失效。

来源不完整、结果被修订、候选改变或解释越界时，受影响主张不能继续沿用原来的已验证标签。

## 7. 个案生命周期、复用与重起

### 7.1 状态机

```text
draft → awaiting_input → frozen → executing → calculated
                                              ↓
                                           validated
                                              ↓
                                          interpreted
                                              ↓
                                           delivered
                                              ↓
                                   observed / closed
```

`execution_failed`、`validation_failed`、`superseded`、`invalidated` 是个案或运行状态，不写进标准子 Skill 的 `status` 字段。

成功产生首次计算结果后就锁定相关执行条件，不等用户看到结果才锁定。解释失败、文本太长或用户不满意不能成为再次取数的理由。

### 7.2 必须冻结的内容

梅花至少冻结对象、事件、命题、判断标准、观察范围、方法、数字或时间输入、时间口径、应期规则及单位。

八字、紫微冻结相关出生资料来源、候选集、规则 profile、目标时间层与分析范围。

无需收集对当前方法没有用途的身份信息。

### 7.3 请求处理表

| 用户变化 | 处理 |
|---|---|
| 结果生成前调整期限、方法或数字 | 修改草稿，重新确认变更字段 |
| 同一对象同一事件要求解释更详细 | 复用原计算结果，只修订解释 |
| 结果后仅把30天改成60天 | 保存范围调整请求；不自动换输入重起，也不外推旧解释 |
| 结果后更换数字、时间口径或算法 | 认定为重起请求，不自动执行 |
| 更换现实对象或出现新的独立事件 | 新建个案，说明与旧事件的区别 |
| 原观察期结束后的新周期 | 可新建个案，先保留原期复盘 |
| 发现可证明的输入、算法或转述错误 | 启动纠错流程，保留旧记录和错误原因 |
| 补充现实信息，但事件未改变 | 更新现实资料与行动建议，不改原始卦象 |

**创建新 ID 不等于获得重新起卦的许可。**

检查必须同时查看事件关系和已存在窗口，防止通过改措辞、改期限或改方法绕过冻结规则。

结果生成前登记的多算法对照属于开发实验，不进入普通占问路径。结果生成后要求“换一种再验证”不追认为独立实验。

### 7.4 复用条件

复用前核对：

```text
subject_ref
event_ref
proposition_id
window
criteria
method_inputs
result_status
provenance
```

任一关键字段不一致，就不能把旧结果当作当前问题的结果。

相同数字、相同卦形、相同时间长度，均不是充分条件。不同个案偶然同卦也不构成相互验证。

### 7.5 存储与并发

默认使用宿主会话状态；有授权时才写入 Skill 目录之外的本地记录区。

最小实现可用受控 JSON 文件和原子替换，不强制引入数据库。

同一个 `case_id + revision + task_id` 一次只允许一个活动执行。重复点击“开始”返回已有状态，不重新获取当前时间。

会话丢失、并发锁不可用或记录无法访问时，必须说明去重保障的实际范围，不能声称跨会话永久避免重起。

## 8. 时间来源、观察范围与精度

### 8.1 来源处理

时间先区分“用户指定的事件时点”和“当前时点”。

用户指定历史时点时，不用系统当前日期覆盖；用户说“现在”时，不沿用旧对话日期。

| 情况 | 处理 |
|---|---|
| 用户给出完整时点与时区 | 原样保留，验证两者一致性 |
| 用户只给18:11 | 仅在本轮日期与已确认时区明确时补齐，并保留来源；否则补问 |
| 宿主提供当前时间 | 保存宿主来源，不伪称用户提供 |
| 只有UTC偏移 | 不据此推断地理位置或唯一IANA时区 |
| 来源互相矛盾 | 标记冲突，确认用户指的是哪个时点 |
| 已冻结指定时间 | 执行、复核、纠错均引用原时点，不悄悄换成新“现在” |

输入只有分钟精度时，内部规范化可以使用秒为零，但必须保留 `input_precision=minute`，不声称事件精确发生在整分整秒。

### 8.2 `now` 的冻结

用户明确采用执行时当前时间时，由受控执行入口一次性读取时钟，保存到个案，再把确定时点传给原生计算器。

原始请求来源仍记为宿主或时钟工具；原生程序收到规范化后的指定时点，不等于该时点是用户手工提供。

技术重试只能使用已经冻结的时点。

### 8.3 期限结构化

保留用户原始表述，同时规范化为起点、终点、边界是否包含、时区和历法口径。

“未来N天”需明确以哪个时点起算；固定24小时日数与当地日历日期不能混用。

“下周面试能否通过”还要区分面试发生周和通知结果的截止时间。

`0 days`、负数期限、无语义字符串、结束早于开始都不能进入正式执行。旧梅花脚本仅接受非空文本的行为可以保留在兼容层，新受控入口承担期限语义校验。

“到起床”“等公司回复”等没有完整终点的范围不得伪造日期。无法规范化又影响正式判断时，只询问该阻塞点。

### 8.4 应期精度

| Profile | 可输出内容 | 禁止内容 |
|---|---|---|
| `stage-within-horizon-v1` | 起始、前段、前中段、后中段、后段、收束 | 平均六等分后生成第几天或具体日期 |
| `moving-line-count-v1` | 按预先固定单位计数，并检查是否落在期限内 | 看到结果后换单位、扩大窗口 |

观察窗口本身可以显示确切日期，但不得因此把象征性的转折阶段写成精确应期。

### 8.5 真太阳时

八字、紫微继续区分原始民用资料、已解析真太阳时和来源等级。

`user_declared` 与 `tool_verified` 不因执行成功而互相升级。

存在时辰、换日、节气或转换参数分歧时保留候选；候选标识必须与命盘一一关联，不根据现实经历选择更顺耳的盘。

## 9. 实际执行与证据等级

### 9.1 执行入口

每个子 Skill 新增一个受控本地入口，例如：

```text
scripts/run-verified.mjs
```

它调用本 Skill 自带的原生计算器，不重新实现取数、十神映射或安星算法。

执行前检查固定入口、源码版本、依赖和冻结输入；执行后捕获退出状态、原始输出和必要运行环境，解析结果并校验。

用户文本通过 JSON 或标准输入传递，不拼接成 shell 命令。脚本入口来自已登记路径，不由用户资料或模型输出任意指定。

### 9.2 执行记录必须包含什么

| 分组 | 必要内容 |
|---|---|
| 绑定 | `run_id`、`case_id`、`revision`、`task_id`、方法标识 |
| 源码 | 仓库提交或发布包标识、实际入口摘要、依赖清单摘要 |
| 输入输出 | 规范化输入摘要、实际输出摘要、可访问结果引用 |
| 环境 | Node、ICU、时区数据、算法与profile版本；未知项如实为空 |
| 过程 | 开始与结束时间、退出码、超时状态、尝试次数 |
| 观察来源 | 宿主工具调用引用、本地runner记录或外部导入来源 |

### 9.3 证据等级不伪装

| 类型 | 含义 | 允许表述 |
|---|---|---|
| `host_observed` | 宿主工具轨迹实际观察到这次执行及输出 | 本轮已执行并检查结果 |
| `local_runner_observed` | 本地受控runner产生记录，但无独立宿主认证 | 本地记录显示已执行；说明验证范围 |
| `imported_unverified` | 用户上传或历史文本中的结果，未复核执行链 | 根据给定结果审阅，未独立重跑 |
| `not_executed` | 仅有文档、代码、计划或模型描述 | 尚未执行 |

观察等级由宿主适配器赋值，不能采信模型或上传 JSON 自报的等级。

若当前宿主只能接收文本记录而无法验证轨迹，就保留较低等级。

**哈希能用于发现内容变化，不能证明真实执行、源码无恶意、输入真实或占断正确。**

本方案不建设密码学远程证明系统，也不宣称 Skill 自己能防住恶意宿主。

### 9.4 技术重试不等于重新起卦

网络读取失败、进程中断、结果文件损坏等技术问题，可以在确认原因后重试同一冻结输入。每次保留不同 `run_id/attempt`。

禁止因为结果不满意改变时点、数字、算法或随机种子。

已有成功输出时优先读取并校验，不重复执行；无法确认首次执行是否成功时，先检查已有记录，必要时做同输入复现并记录原因。

### 9.5 两阶段包装：计算器不负责生成解释

受控入口不能仅凭计算成功自动生成一份含结论的标准子结果。

```text
compute(frozen_case, task)
    → execution_record + native_result_ref

interpret(task, validated_native_result, selected_knowledge_cards)
    → interpretation_draft

finalize(execution_record, native_result, interpretation_draft)
    → execution_bundle
```

`compute` 由代码完成。

`interpret` 由相应子 Skill 的模型上下文完成。

`finalize` 由代码检查绑定、格式、依据引用和事实一致性，再封装标准子结果。

解释校验失败只修改草稿，不重新调用原生计算器。不同方法的原生载荷结构分别适配，不能用一个通用合并函数覆盖其来源字段。

给定命盘审阅另走已登记的 `provided_chart_review` 来源路径：可以检查和解释合格的给定资料，但执行记录明确哪些检查实际执行、排盘是否由外部提供，不宣称本轮重新排盘。

## 10. 校验与受控输出

### 10.1 六道检查

| 检查 | 内容 | 不通过时 |
|---|---|---|
| G1 输入 | 对象、期限、方法、时间来源、参数合法 | 只补问阻塞输入 |
| G2 执行 | 调用来源、固定入口、退出码、输出完整性 | 停止依赖计算的解释 |
| G3 原生结果 | schema、枚举、输入回显、卦形或命盘结构 | 保留诊断，不生成结论 |
| G4 绑定 | case、task、subject、proposition、版本一致 | 禁止复用和综合 |
| G5 解释 | 依据可定位、范围符合能力、事实与象征分开 | 修订解释，不重新计算 |
| G6 交付 | 最终事实块与原生结果一致、未完成分支可见 | 修复转述或降级交付 |

G1—G4 和 G6 的结构化部分是程序硬检查；G5 和自然语言的全部含义只能部分自动检查。

### 10.2 计算事实不交给模型重写

时间、卦名、动爻、阴阳变化、上下卦、互错综卦、体用、星曜位置及已声明岁运等事实，由固定渲染器从已校验数据生成。

模型输出解释草稿时引用事实标识，不重新计算这些字段。

详细事实可以折叠为摘要或审计附件，但不能因简洁而改写数值或隐去关键限制。

### 10.3 标准子结果

继续使用 `ok`、`insufficient_input`、`error` 三个子状态。

`ok` 需要合格执行或被允许的来源路径、可用载荷及至少一项符合范围的主张；非 `ok` 的 `claims` 为空。

八字仅完成结构检查但真太阳时来源未确认时，可按现有契约保存结构事实，不因此生成旺衰或求职成败结论。

原生输出 `ok` 也不自动等于解释层完成。

### 10.4 错误映射

保留现有路由区分：能力不支持、能力未加载、依赖不可用、资料不足、执行失败、契约不兼容。

新校验细节写入验证报告，不随意扩充旧状态枚举。

一个分支失败时，可以交付其他仍独立有用且实际完成的分支；不能给失败分支补造“简版结论”。

## 11. 运行环境兼容与独立分派

### 11.1 能力必须逐项判断

```text
skill_loading: file_read | native_activation | unavailable
process_execution: available | unavailable
chinese_calendar: verified | unavailable | unknown
branch_isolation: verified | unavailable | unknown
tool_observation: available | unavailable
case_store: session | authorized_persistent | unavailable
```

Skill 激活与子代理分派是不同能力。文件读取可以合法加载 Skill；出现激活标签不证明另建了独立上下文。

### 11.2 三种执行结果

| 环境 | 允许行为 |
|---|---|
| 可读取Skill并运行脚本 | 执行单方法，不要求必须有原生Skill调用工具 |
| 还具备可验证的独立分支上下文 | 执行组合，各分支只接收任务相关输入 |
| 缺少必要执行或隔离能力 | 返回计划或明确部分完成，不称为独立三法核验 |

本版不把同一模型上下文中的依次解读包装成严格独立执行。

明确要求组合但隔离不可用时，说明缺口；不擅自选择用户未同意的替代方法。

### 11.3 隔离的验证对象

检查的是送入分支的上下文是否包含其他方法输出，不是只检查 `branch_id` 是否不同。

每个分支记录输入清单摘要，主路由在结果冻结后才接收其解释。

原生计算引擎的 VM 隔离也不等于语言模型上下文隔离。Node 官方明确指出 `node:vm` 不是用于执行不可信代码的安全机制；现有 VM 适用于候选配置隔离，不能宣称安全沙箱。

### 11.4 防递归

一个顶层请求只有一个活动的主路由实例。

主路由不能分派自身；子 Skill 遇到职责变化时返回给当前主实例，不再启动嵌套主路由。

同一实例重新读取 references 不算递归。UI 重复出现Skill标签也不直接判为递归；依据实际调用链和父子任务标识判断。

## 12. 综合分析：只比较真正可比较的主张

主路由只消费子结果 `claims[]`，不从原生载荷再推导新的术数结论，也不让后执行的分支迎合先执行的结果。

### 12.1 比较规则

先确认对象、事件、命题、判断标准、时间尺度和窗口，再看方向。

本次新执行profile采用更保守的窗口规则：

**形式上的“一致/冲突”只用于同一规范窗口或同一周期标识。**

仅有窗口重叠、包含关系或自由文本相似时，不自动把两个命题视为等价。

同样叫“2026年”，立春年界与农历新年年界也不自动相同。不得由主路由把年度结论自行缩小到某个月。

| 标签 | 条件 |
|---|---|
| `consistent` | 同一可比较命题，方向一致 |
| `conflict` | 同一可比较命题，方向明确相反 |
| `complementary` | 对同一现实目标提供不同层面的信息，但不构成相互验证 |
| `not_comparable` | 对象、范围、条件、方向或来源无法满足比较要求 |

“互补”单独判断，不先要求时间层完全相同再称其层面不同。无法判断关系时保留不可比较，不强行合成统一答案。

### 12.2 组合不制造确定性

八字职业背景、紫微年度事业主题与某次面试的梅花个案，可以分别陈述，但不能共同推出“这次面试必过”。

三个方法只有在用户明确要求、职责真实存在且各分支可执行时才使用。

缺一项就显示缺一项，不用星级、百分比或多数票掩盖覆盖不足。

### 12.3 综合结果的呈现契约

总体输出同时保存 `requested_methods`、`completed_methods` 和未完成原因。

`overall_status=ok` 仅说明当前被接受的任务范围已经按契约完成，不说明预测确定。

用户请求范围未完整覆盖时使用部分完成；不能事后缩小“实际接受范围”来伪造完整完成。

每项综合建议标明引用了哪些方法主张、哪些现实资料。建议可以主要由现实信息支持，但不能贴上“三法共同证实”的标签。

## 13. 解释知识卡与推断边界

### 13.1 分层表达

每项内容标明其性质：计算事实、传统解释、现实事实或行动建议。

来源保存在内部结构，普通答复用自然语言体现，不强制展示字段名。

传统解释不用于断定他人隐藏思想、失物精确位置、设备隐藏故障、账号风控批次或医疗结论。

即使开头写了“仅供参考”，正文也不能再作上述确定断言。

用户说“很准”只是反馈，不自动记录为验证成功。事后得知的事件不得写回原预测，也不能用于选择更有利的流派或候选盘。

### 13.2 知识卡字段

| 字段 | 内容 |
|---|---|
| `card_id`、`version` | 稳定标识与版本 |
| `tradition_profile` | 所采用体系及适用范围 |
| `sources` | 可核查的来源、定位及许可信息 |
| `meaning` | 必要的传统含义 |
| `prerequisites` | 使用该解释需要的结构 |
| `counter_readings` | 至少一项相反或缓和解释 |
| `not_inferable` | 不能据此断定的现实事实 |
| `fact_requirements` | 需要引用的计算字段 |

来源只能支持“该传统如何解释”，不能因此证明现实预测有效。

### 13.3 最小知识范围

**梅花：**先补八卦语义、六十四卦的简明主题与解释边界；未完成来源审阅前，不扩展成三百八十四爻的自动断语库。

**八字：**先补旺衰、调候、格局、合化条件、用神目标函数和神煞政策，不生成统一吉凶评分。

**紫微：**先补十四主星、四化及事业、迁移等已支持领域的组合解释框架，不凭单星生成现实事件结论。

知识卡缺失时缩小解释范围，不调用模型记忆伪装成“库内依据”。

新知识卡必须经过来源、反证、边界和合成用例审查。

### 13.4 现实建议独立更新

新测评、报价、面试反馈或关系沟通事实可以改变现实行动建议。

记录建议的修订原因，但保留原始计算结果和原解释版本。

不把“现实信息支持购买”改写成“卦其实早就支持购买”，也不把一般安全建议描述成卦算出的特定危险。

## 16. 用户交互与纠错

### 16.1 减少重复确认

用户已经确认的时间口径、方法偏好和输出深度可以在适用范围内复用。

问题、对象、窗口、判断标准齐全后直接执行，不机械要求再回一次“开始”。

缺少真正阻塞的字段时合并询问。时间法不用询问出生资料；数字法不用索取无关地点；购买题不能自行发明价格阈值。

普通问题采用简短输出：

**主要倾向、关键依据、限制、现实可行动项。**

完整算式、运行版本、载荷放入审计模式，不能把每个日常问题写成研究报告。

### 16.2 结果不是强制二选一

区分“当前信息支持的行动建议”与“传统象征解释”。

不能判断时可以明确不下成败结论，不为满足“直接说”而虚构确定性。

健康、安全或强烈情绪困扰场景先处理现实需求；不能用卦替代医疗判断、休息安排或现实风险证据，也不推动因焦虑反复起卦。

### 16.3 纠错流程

发现错误后：

```text
确认错误类型
    → 标记受影响结果
    → 保留原记录
    → 按正确且明确的依据复核
    → 重新生成受影响的解释
    → 告知哪些旧结论失效
```

纠错必须说明旧结论哪些失效，不能只悄悄换一个卦名。

因转述错误修复文字不算新起卦；因输入错误重新计算要保留原记录及更正来源。

仓库根目录的开发文档、测试、夹具、构建缓存不进入正式包。

## 18. 测试体系与发布门禁

### 18.1 四层测试

| 层级 | 验证内容 | 运行位置 |
|---|---|---|
| 单元测试 | 数字、卦形、日期、时辰、解析和固定关系 | 每次提交 |
| 契约测试 | schema、状态、来源、引用、绑定、版本 | 每次提交 |
| 集成测试 | 包装器→原生脚本→子结果→路由及独立安装 | 每次提交及发布 |
| 对话行为测试 | 重起、串案、伪执行、读心、缺分支、精度漂移 | 发布前指定模型与宿主矩阵 |

确定性测试可使用 Node 内置测试运行器，具体运行时版本由项目锁定。审计所用版本是复现基线，不自动作为永久推荐版本。

### 18.2 必须覆盖的回归场景

| 编号 | 场景 | 预期 |
|---|---|---|
| T01 | 64卦×6动爻 | 本变互错综、体用关系满足结构不变量 |
| T02 | 余零、两数、三数、整数上限 | 按固定协议处理或明确失败 |
| T03 | 00:59/01:00、22:59/23:00等边界 | 正确时支；午夜与子初规则不混用 |
| T04 | 闰月、无效日期、DST缺口与重复时段 | 保留历法标记或拒绝歧义输入 |
| T05 | 偏移与IANA时区不一致 | 预检阻止执行 |
| T06 | 零期限、负期限、无意义期限 | 不能作为正式观察窗口 |
| T07 | 两个对象使用相同数字 | 不复用个案或结论 |
| T08 | 同一对象的感情与求职问题 | 不跨命题复用 |
| T09 | 输出后改30天为60天或换方法 | 不自动重起，不回填独立验证 |
| T10 | 重复点击开始、技术重试 | 同一冻结输入，禁止重新取当前时间 |
| T11 | 只有源码读取，无执行 | 不宣称已起卦或已核盘 |
| T12 | 原生JSON损坏、重复键、来源伪装 | 拒绝或降为未验证导入 |
| T13 | 最终文本卦名、时辰与载荷不一致 | 交付前修复或阻断 |
| T14 | 相对阶段被细化成具体日期 | 精度检查不通过 |
| T15 | 八字来源未确认 | 只做允许的结构检查 |
| T16 | 紫微只有民用资料或vendor损坏 | 不回退、不造盘；原因明确 |
| T17 | 多分支声称独立但上下文共享 | 禁止标为严格独立组合 |
| T18 | 方法清单、调用目标、返回版本冲突 | 不进入综合 |
| T19 | 重叠但不相同的观察窗口 | 不自动标一致或冲突 |
| T20 | 缺一个分支仍称“三法完成” | 检查覆盖声明失败 |
| T21 | 用户认可或补充事后结果 | 不自动升级证据或改写预测 |
| T22 | 失物、他人动机、设备故障等隐藏事实 | 不以符号断定现实事实 |
| T23 | 单独复制每个Skill、断开网络 | 本地能力正常；外部依赖明确缺失 |
| T24 | 包中夹入测试、个人资料、日志或外部软链接 | 打包检查失败 |

测试夹具全部合成，不复制真实姓名、生日、关系经历、账号来源或聊天记录。

具有普遍意义的错误只转写为脱敏场景结构。

### 18.3 不只测“能通过”，还要测“能拦住”

加入反向测试：

**改动一个卦名、交换对象标识、删执行引用、把阶段改日期、篡改引擎分块。**

验证器必须捕获这些注入错误。

算法测试的期望值不能全部由被测函数自己生成。使用经过审阅的独立规则表、合成黄金样例与结构不变量组合，避免两边共享同一错误。

### 18.4 门禁指标

所有确定性与契约测试必须通过；声明支持的宿主和模型组合必须完成对应测试。

Critical 行为违规在发布验收集上必须为零，但这个数字不表示现实使用中绝不会失败。

未测试环境列为“未验证”，不能因为同品牌或同模型家族就标为兼容。

不把加载成功、脚本成功、端到端成功混成一个通过率。

还要记录每任务资源读取数、输入上下文、工具次数、执行耗时和载荷大小。测量后控制回归，不虚构固定的跨模型 token 成本或性能提升比例。

### 18.5 持续集成流水线

```text
检查源码与运行依赖锁定
    → 检查生成副本及引用路径
    → 单元与契约测试
    → runner集成与故障注入
    → 允许清单构建四个独立包
    → 临时目录逐包安装、离线冒烟
    → 发布前运行指定宿主/模型行为矩阵
    → 检查隐私、许可、版本与产物摘要
    → 生成候选发布包与测试报告
```

发布前的语言模型测试可能需要外部服务，因此与不需要密钥的确定性PR测试分开。

报告记录模型实际标识、宿主、参数和执行时间；复测时保留全部结果，不只展示通过的那一次。

行为测试不能仅用被测模型自己打分；结构违规由代码判定，语义违规使用独立复核和合成金标准，争议样例人工确认。

## 19. 协议版本与迁移

### 19.1 保留算法，升级真正改变语义的编排部分

| 对象 | 本次版本处理 |
|---|---|
| `lunar-time-v2`、`numbers-v2` | 保持不变，不就地改算法 |
| `cast-meihua/result-v2` | 保持原生格式 |
| 八字检查器原生 `schemaVersion: 1.0.0` | 保持，新增能力另立版本 |
| `ziwei.input.v2`、`ziwei.facts.v2`、当前排盘profile | 保持；不借可靠性改造改变安星口径 |
| `metaphysics.standard-child.v1` | 保持既有字段和语义 |
| 个案、时间、执行记录、bundle | 新增独立v1契约 |
| 编排执行profile | 实现完成后新增 `method-v5` |
| 路由计划、任务、适配、总结果 | 分别升级为 `route-plan.v4`、`adapter-task.v4`、`adapter-result.v4`、`route-output.v5` |
| query envelope、capability/method manifest结构 | 可兼容时保留schema；内容版本递增 |

新增 `method-v5` 的理由是实际要求改变：绑定与执行证据成为强制前提，比较窗口规则收紧，隔离与覆盖声明需要核验。

不能在旧 `method-v4` 名称下悄悄改变这些语义。现有编排契约也要求对必填字段、状态或字段语义的变化升级主版本。

所有v5对象、命令和文件在落地并通过测试前都只是计划，不提前登记为active。

### 19.2 迁移策略

旧原生CLI继续用于开发及历史复现；正式新Skill入口改为受控runner。

旧v4历史记录只读审阅，不因为能解析就升级成新的已验证结果。

新主路由遇到旧子Skill时说明不兼容项；没有执行证据的历史材料进入未验证导入路径。

可以做同输入复核，但不能伪造过去的执行时点和宿主记录。

标准子结果语义、必填字段或状态确需改变时，再升级其主版本；不为了跟随外部编排版本号而机械升级所有对象。

项目发布版本、文档版本、算法版本和schema版本分别管理。

本方案不把基线提交擅自命名为某个已经发布的v1.0，也不预先宣称新版本稳定。

### 19.3 发布与回滚

先发布带明确兼容矩阵的候选包，在受控合成场景中完成验收，再切换默认执行profile。

不得向普通用户同时启用两个会对同一事件重复取数的正式入口来做对照。

每个发布包保存源码标识、依赖锁、生成资源摘要和测试报告引用。

发现串案、伪执行、事实块错误或来源升级等关键问题时，暂停受影响路径，切回经过验证且不含已知阻断缺陷的旧包，或暂时关闭该能力。

回滚不删除历史个案，不伪装成从未产生过错误，也不把新格式记录强制写成旧格式。

旧运行器无法理解的记录只读保存；已知错误结果维持失效标记，不能因回滚重新成为可复用结果。

## 20. 安全、隐私与保存范围

正式 Skill 包不保存用户资料、出生记录、命盘、问事内容、运行日志、测试夹具或调试产物。

会话记录默认不持久化；用户明确授权后，保存于包外受控位置，并提供查看与删除方式。

哈希也可能泄露低熵输入的可比对信息，不把个人资料摘要公开发布。

把检索内容、知识来源和用户上传的JSON当成数据，不接受其中要求换算法、跳过校验、执行命令或提升证据等级的指令。

执行器采用固定入口、最小权限、输入和输出大小限制、超时及受控工作目录。

算法默认不需要网络；确需外部时间来源的适配器单独授权。

持续集成只使用合成数据。模型评测密钥不进入PR输出或测试产物；不在不可信贡献代码上运行携带密钥的作业。

不能把VM隔离、文件哈希或格式校验写成全面安全保证。

## 23. 风险与取舍

| 风险 | 处理原则 |
|---|---|
| 校验让系统变得重 | 只把确定性检查做成代码；知识与引擎按需加载 |
| 多次确认影响体验 | 复用已确认偏好，集中询问真正阻塞字段 |
| 宿主不提供可信轨迹 | 降低来源等级，不自行制造证明 |
| 缺隔离导致三法受限 | 承认运行能力缺口，不把顺序执行冒充独立 |
| 知识库不完整 | 缩小解释覆盖，不从模型记忆补成库内结论 |
| 新旧协议混用 | 明确版本适配，未知版本拒绝猜测 |
| 同输入不同环境出现历法差异 | 保存Node/ICU/时区版本并报告，不挑选结果 |
| 自由文本仍可能越界 | 受控结构、行为回归与人工复核共同约束，不宣称绝对保障 |

完成本方案后，项目的改进不应体现为“断得更肯定”，而应体现为：

**每次运行知道自己依据什么、实际做了什么、哪些部分没做，以及结论能够说到哪里。**
