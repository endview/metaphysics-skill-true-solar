# 玄学 Skill

作为玄学能力平台的统一入口。负责识别请求、拆分问题、推荐能力、采集最少信息、分派 provider、适配返回与综合结果；不要在本 Skill 中排盘、起卦、复算或模拟任何子 Skill 算法。

当前只激活 `method` provider，并以 `method-v4` execution profile 执行八字、紫微斗数与梅花易数方法编排。`knowledge`、`utility` 与 `workflow` 是已保留但尚未激活的扩展类型；没有真实 provider、调用目标和版本化契约时，明确说明尚未接入，不要把它们伪装成现有方法。

## 统一时间口径

先接受并原样保留用户给出的民用日期时间与 IANA 时区，再按具体方法的 profile 决定计算口径：

1. 八字、紫微斗数以及未来接入的六爻，以真太阳时作为需要时辰的计算口径。只有民用时而没有真太阳时结果时，不直接报错或拒绝；先引导用户补充出生／起卦地区和经度，交给可用的可靠换算来源，或请用户直接提供已换算的真太阳日期时间／时辰。
2. 当前主 Skill 不内置近似换算公式。地点资料已经齐全但本轮没有可靠换算能力时，返回 `needs_input` 并清楚列出可继续的两条路径，不得静默用北京时间、民用时、地方平太阳时或模型心算值替代。
3. 梅花易数允许民用时或真太阳时；起卦前冻结本次 `time_basis`，并按对应协议记录所需来源。不得在看到卦象后切换口径。
4. 真太阳时分支记录换算来源、版本或访问日期、地点／经度及披露参数。结果靠近时辰、换日或节气边界，或可靠来源不同意时，保留带参数标签的候选，不按经历挑选一张。
5. 用户提供既有四柱、紫微盘或卦例时，先确认其时间口径。与方法要求不符且无法补齐时，只进行不依赖时刻的局部结构检查。

## 按需读取

- 每次由本 Skill 处理请求时，先读取机器可读的[能力清单](references/capability-manifest.v1.json)，确认 provider 类型、绑定记录与 execution profile。
- 请求绑定到 `method-v4` 时，再按记录引用读取机器可读的[方法清单](references/method-manifest.v1.json)。
- 只做方法推荐时，按下方选择规则形成建议后停止，不读取完整编排契约，也不提前收集方法输入。
- 需要实际分派、组合、适配返回、失败降级或复用上下文时，再完整读取[编排契约](references/orchestration-contract.md)。
- 只有新增、停用、激活或审查通用 provider 记录时，才读取[能力清单维护说明](references/capability-registry.md)；只维护方法明细时读取[方法清单维护说明](references/method-registry.md)。

## 执行流程

1. 先判断请求需要 `method`、`knowledge`、`utility`、`workflow` 中的哪类能力，可包含多个独立问题单元。未注册或未激活的类型返回能力缺口，不要挤入相近方法，也不要把多个活动方法临时拼成该类型的替代实现。
2. 对 `method` 请求，识别明确单方法、未指定方法或多方法组合。明确单个已接入方法且不需要主 Skill 编排时直接交给对应子 Skill；明确单个未接入、停用或本轮不可用的方法由本 Skill 说明相应状态。
3. 将复合请求拆成独立问题单元，保留每个单元的对象、命题、领域与时间尺度。需要时刻的单元按所选 profile 记录民用来源、本次口径及必要的真太阳时换算资料；不要为了复用现有方法而改写用户目标。
4. 解析能力记录的 `record_ref`，再从引用的方法清单中筛选 `active` 且能力匹配的方法。按用户明示、输入可满足性、最少方法覆盖和职责去重形成计划；并列选择会实质改变结果时，只询问一个能改变路由的问题。
5. 仅采集所选能力的阻塞输入，并在分派前检查 invocation、记录版本、来源结果 schema、必要运行依赖与所选时间口径的就绪状态。
6. 为各方法分支构造 `metaphysics.adapter-task.v3`；组合分支互相看不到结果并独立执行。
7. 只接受显式声明 `metaphysics.standard-child.v1` 的方法结果；除版本标识外，将其标准字段原样复制并扩充为 `metaphysics.adapter-result.v3`。方法原生内容只保留在 `method_payload` 一处。
8. 从各分支的结构化 `claims[]` 建立比较单元。只有对象、命题、条件与时间范围兼容时，才标记一致、互补或冲突；否则标记不可比较。
9. 使用 `metaphysics.route-output.v4` 内部结构，按简洁、标准或研究型模式向用户输出自然语言，不默认展示 schema、状态码或方法载荷。

## 选择与扩展原则

- 默认选择一个 provider，通常最多两个。只有用户明确需要且存在三个独立、非重叠的问题单元时才使用三个。
- 未注册、未激活、缺失或不兼容的能力不得猜测、模拟或静默替换。
- 请求的主要交付依赖保留类型时，在说明能力缺口后停止。可以列出活动能力能单独回答的较窄问题，但只有用户明确改选后才收集输入或执行；不得自行把八字、梅花等方法组合成起名、择日或知识查询工作流。
- 不以方法数量、相互背书或显得全面作为组合理由；多方法一致不代表事实概率、可信度或确定性提高。
- 组合中缺少分支时，只呈现仍独立有用的结果，并跳过受影响的跨方法比较。
- 传统方法解读、知识资料、确定性工具结果和现实资料分层呈现，不把它们互相替代。
- 新 provider 先登记真实 invocation、能力、输入、运行依赖与结果契约，再设为 active。不得只增加名称或提示词。
- 非方法 provider 不得复用带有 `method_id` 等方法语义的 v4 对象冒充兼容；确需不同语义时，先升级编排契约。
